# Change request: `project-guide` owns its own shell completion — add a `completion` command group

**Target repo:** [`project-guide`](https://github.com/pointmatic/project-guide).
**Consumption:** pyve today hand-writes a Click completion snippet into the user's `~/.zshrc` / `~/.bashrc` (`add_project_guide_completion` in `lib/utils.sh`). On the version of project-guide that ships this command, pyve **retires its own block** and shells out instead — a real min-version dependency (`project-guide >= <first release with `completion`>`), plus a one-time cleanup of pyve's legacy sentinel block.

---

## Problem statement

project-guide is a Click application, and Click ships a completion protocol: setting `_PROJECT_GUIDE_COMPLETE=<shell>_source` in the environment makes the binary emit a shell-specific completion script. Click's conventional packaging of this is a `completion` subcommand that the tool provides for itself. **project-guide has none** — `project-guide --help` lists no such command.

In its absence, **pyve reached into project-guide's internals** and hand-rolled the wiring: it appends a sentinel-bracketed block to the user's rc file that sets `_PROJECT_GUIDE_COMPLETE=zsh_source`, runs the binary, and evals the result. That block has now failed in the field twice, and both failures trace to pyve having to model a protocol it does not own:

1. **The block assumed zsh's completion system was initialized.** Click's `zsh_source` output ends in `compdef _project_guide_completion project-guide`. `compdef` does not exist until `compinit` has run. On a shell whose startup files never run `compinit`, the eval died with `command not found: compdef`. pyve had no reason to know this was a precondition — it is a property of Click's generated script.
2. **The block resolved `project-guide` through `PATH`.** pyve hosts project-guide in a private toolchain venv with a `~/.local/bin` shim, and that directory is not always on `PATH`. The guard `command -v project-guide` was simply false, and the block evaluated nothing.

Both failed **silently**. The user's report ([pyve#70](https://github.com/pointmatic/pyve/issues/70)) opens with the symptom that matters: *"typing `project-guide <TAB>` offers nothing, and no error is printed."* Defect 1 masks defect 2 — the eval never runs, so its error never prints.

**The framing that motivates this request:** after pyve provisions project-guide, it does not *act installed*. `project-guide --version` works and `pyve self provision --status` reports ready, but the affordances a user associates with an installed CLI — invocable by name, tab completion — are absent or broken. Half of that (reachability of the shim directory) is squarely pyve's problem and is being fixed pyve-side. The other half is project-guide's: **a tool should know how to install its own completion.**

pyve has patched its block (absolute-path resolution + a `compinit` bootstrap) so users are not stranded while this lands. That patch is explicitly interim — it is pyve tracking another tool's protocol, which is the coupling this request removes.

---

## Proposed change

Add a `completion` command group to project-guide:

```
project-guide completion install [--shell auto|zsh|bash|fish] [--bin <path>] [--rc <path>]
project-guide completion uninstall [--shell auto|zsh|bash|fish] [--rc <path>]
project-guide completion show [--shell auto|zsh|bash|fish]
project-guide completion status
```

### 1. `install` — own the whole wiring, including its preconditions

Write a sentinel-bracketed block to the user's rc file. Idempotent: a no-op when project-guide's own sentinel is already present. The emitted block must satisfy the two properties pyve learned the hard way:

- **Do not depend on `PATH` resolution.** The block should reference an absolute path. See `--bin` below for which one.
- **Do not assume `compdef` exists** (zsh). Bootstrap the completion system when it is absent, re-check, and skip registration rather than erroring:

  ```zsh
  (( $+functions[compdef] )) || { autoload -Uz compinit && compinit -i; } 2>/dev/null
  ```

  When the user's own config already ran `compinit`, leave it alone. bash needs no equivalent — `complete` is always available.

- **Degrade silently.** Completion is a convenience; a broken or missing install must never emit noise at every shell startup.

Consider also offering the **`fpath` route** as an alternative or default for zsh: the generated script carries a `#compdef project-guide` header and an explicit `loadautofunc` branch, so it can be written once to an autoload directory instead of being regenerated by a subprocess on every shell start. That sidesteps the `compdef` ordering problem entirely and removes a fork from shell startup. It still requires `compinit` to run, so the bootstrap above remains necessary.

### 2. `--bin` — let a host tool supply the stable handle

**This is the part that matters most for pyve.** The naive implementation writes `sys.argv[0]` (or the resolved console-script path) into the rc block. Under pyve hosting that is:

```
~/.local/share/pyve/toolchain/<PYTHON_VERSION>/venv/bin/project-guide
```

— a **version-keyed** path. pyve's toolchain slot is keyed by its default Python version, so that path changes when pyve bumps its pin, silently rotting the user's rc block. The stable handle is pyve's shim, `~/.local/bin/project-guide`, which pyve re-points with `ln -sf` on every bump.

So: `--bin <path>` lets the host tool declare which path to bake in. pyve will pass its shim. Resolution order when `--bin` is absent: project-guide's own resolved absolute path, then a bare-name `PATH` fallback for a hand-installed copy.

### 3. `uninstall` — remove project-guide's own sentinel block

Byte-clean removal so `install` → `uninstall` round-trips. Needed for pyve's `self uninstall` path and for users who want it gone.

### 4. `status` — report whether completion is wired, and for which shell

Lets a host tool (and `project-guide heal`) answer "is completion actually installed?" without parsing rc files. Worth reporting *stale* wiring too: a block whose `--bin` path no longer resolves.

### 5. Detect and adopt pyve's legacy block

Users already carry pyve's sentinel:

```
# >>> project-guide completion (added by pyve) >>>
… 
# <<< project-guide completion <<<
```

`install` should detect that exact sentinel pair and either replace it or refuse with a clear message, so users do not end up with two blocks registering the same completion. (pyve will also remove its own legacy block on the upgrade path; belt and braces, since the two tools upgrade independently.)

---

## Motivation

- **The protocol belongs to the tool that generates it.** Every property pyve got wrong — the `compdef` precondition, the `loadautofunc` branch, the fact that `zsh_source` output must be eval'd rather than autoloaded — is a fact about Click's generated script, not about pyve. project-guide is the only component that can track those as Click evolves.
- **It removes a silent-failure class outright.** pyve's block had no way to report its own failure: the guard failed silently by design and the generator's stderr was suppressed (deliberately — an asdf shim can be noisy there). A first-class `completion install` can validate at install time, and `completion status` can be checked later.
- **Every other consumer benefits.** Anyone who installs project-guide by any route — pipx, a plain venv, a future host tool — gets completion with one command instead of a hand-copied snippet from the README.
- **It is the conventional shape.** `gh completion`, `rustup completions`, `poetry completions`, `uv generate-shell-completion`. A Click app without one is the outlier.

---

## Compatibility notes

- **Purely additive.** A new command group; no existing behavior changes. Consumers on older project-guide versions are unaffected.
- **No pyve min-version dependency in the other direction** — project-guide needs nothing new from pyve. `--bin` is an optional flag that any caller may ignore.
- **pyve's coordinating change** lands separately and waits for the release that ships this: pyve replaces `add_project_guide_completion` with a call to `project-guide completion install --bin "$HOME/.local/bin/project-guide"`, keeps `remove_project_guide_completion` long enough to clean up legacy blocks on upgrade, and drops its hardcoded knowledge of `_PROJECT_GUIDE_COMPLETE` entirely. pyve's interim fix stays until then.
- **Not in scope for this request:** whether `~/.local/bin` is on the user's `PATH`. pyve chose that shim location, so pyve owns its reachability; it is tracked as a separate pyve-side story. This request only asks that completion not *depend* on `PATH` resolution — which `--bin` satisfies.

### Where the boundary falls, and why

project-guide is an ordinary pip package in a virtualenv. It can be installed again and again, any number of times, in any number of environments — and it has no concept of, or responsibility for, there being **one** copy shared across a developer's repos. That single-global-install construct is entirely pyve's invention (a private toolchain venv plus a `~/.local/bin` shim), so every particular of it — which binary is canonical, where it lives, whether it is reachable from the user's shell — is pyve's to own and is being fixed pyve-side.

What is *not* pyve's to own is how a Click application generates and registers its own completion script: that the `zsh_source` output terminates in `compdef`, that `compdef` presupposes `compinit`, that the script carries a `#compdef` header with a `loadautofunc` branch making the `fpath` route viable. Those are properties of project-guide's generator, they change when Click changes, and pyve can only track them by guessing — which is precisely how both field defects arose.

Hence the split this request assumes: **project-guide owns the protocol; the host tool supplies the path.** `--bin` is the whole of the interface between them.
